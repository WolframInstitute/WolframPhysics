# Cross-Listing Audit

Summary: the guide tree is thematic, so a function may sit on every page whose subject needs it, yet the split that produced the 35 pages assigned most entries to one page. This audit parsed every entry of every page (3517 bullets, 2578 distinct names over the 28 leaf pages, the seven hubs and the root), read each leaf's abstract and section headings for its subject, and looked for entries elsewhere in the tree that fit that subject and are absent from the page by name. It proposes 400 cross-listings (one row per function and source, 435 page placements over the 28 leaves) and records 20 Function Repository twins of functions the pages list from Stephen Wolfram's writings, the technical introduction program files or the nikm cloud deployment. Nothing was changed on a page; this report and the structured rows are the proposal.

## Method

Run on 2026-09-21 from the shell (python3 for the parse, curl for URL checks) and from a WL 15.0 kernel that is not cloud connected (wolframscript -file on a scratch .wls under the session scratchpad, xlist/twins.wls). Scratch files: xlist/parse_pages.py, xlist/candidates.py, xlist/decisions.json, xlist/build_rows.py, xlist/twins_rows.py.

1. Parse. Every `- ` bullet of every page under docs/en/Guides was parsed into entries: the leading chip or link (a bare backtick chip, a link whose text is a code span, or a plain-text link for a post or a program file), the provenance tag in parentheses or, under a per-source `### ` heading, that heading as the source, the description when the bullet is an annotated single entry, and the section it sits in. A tail bullet of comma-separated chips or links yields one entry per item. Sources were normalized to the inventory's spelling (WFR for both the tag and the heading, Cloud:account for a nikm cloud function, GitHub:owner/repo for a bare GitHub link).
2. Subjects. For each of the 28 leaves the abstract and the thematic section headings were read and taken as the page's subject; the per-source headings were not, since they are an arrangement of the page and not a topic.
3. Candidates. For each leaf a concept vocabulary was searched over the name and the description of every entry on the other pages (Multiway, TokenEvent and Multihistory for the multiway page; Causal, LightCone, Foliation and Event for causal graphs; Branchial, branch pair, entanglement and quantum circuits for branchial graphs; Rulial, rule space and observer for rulial space; Canonical, Isomorphic, Automorphism and equivalence classes for canonicalization; Dimension, ball growth, sprinkling and lattice for dimension; Curvature, Ricci, Einstein and the tensors for curvature; Geodesic, Distance, Ball, interval, embedding and coordinates for geodesics; Gauge, Holonomy, Connection, Bundle, Hodge and Dirac for gauge fields; incidence, betweenness, simplicial, tessellation and topology for synthetic geometry; CausalSet, Poset, chain, antichain and sprinkling for causal sets; Lorentz, foliation, observer, light ray and gravity for relativity; Combinator; Lambda, beta, redex and Curry-Howard; TuringMachine; CellularAutomaton, Substitution and TagSystem; Automaton, Petri, register and network system; Proof, prover and sequent; Axiom, Entailment, Completion, Equational, critical pair, model and algebra; Category, Functor, Pushout, Presheaf and homotopy; Diagram, ZX and circuit; Plot, Draw, Style and Graphics; rule enumeration, numbering and classification; evolution objects, growth and events; engines, sessions, bounds, parallel kernels and solver links; and the plain graph vocabulary). The search produced between 12 and 790 candidates per page.
4. Judgment. Each candidate was judged against the page's abstract, not its name: it was kept when a reader of that page would look for it there (a multiway Turing machine function on the multiway page, a linear extension on the causal graph page beside the sequential orderings its abstract names, a sprinkling on the dimension page as a test space of known dimension) and dropped when the match was a word only (the causal states of computational mechanics are not causal graphs; a Petri net read as a category is a category, not an automaton; the Tarski dimension axioms are not a dimension estimate). Entries already present on the page under any source were excluded by name; the page body was read in full for every leaf to confirm the absences.
5. Descriptions. The description of each row is copied from the page that annotates the entry. Where the entry appears only in a tail bullet or under a per-source heading with no description anywhere in the tree, a one-line description was written from the source's own usage text in the inventory (docs/research inventory merged.json), and the row's evidence says so.
6. Twins. Every function the pages list from the writings, the technical introduction program files or the nikm cloud deployment (158 names, with singular and plural and capitalized variants, 372 names in all) was resolved as a bare ResourceObject name in the kernel; four resolved (FindBooleanAlternative, GraphAntipodes, HardSphereSimulation and Geodesic, the last a surface-geodesic function unrelated to the graph function of the same stem). The semantic twins were then curated from the pages themselves, matching what a writings function computes against the Function Repository entries already in the tree (MultiwayCombinator for MWCombinatorGraph, TagSystemEvolveList for TSEvolveList, MultiReplace for TwoWayStringReplaceList, and so on). The one twin new to the tree, HardSphereSimulation, was fetched at https://resources.wolframcloud.com/FunctionRepository/resources/HardSphereSimulation/ (HTTP 200, page titled with the function's name; the nikm cloud copies of unpublished functions redirect to a sign-in page instead).
7. Checks. Every URL in the rows is one the tree already carries, except the HardSphereSimulation resource above. No built-in was newly tagged: every `(WL)` chip proposed is a chip some page already carries with that tag. The lint (scripts/lint_docs.wls) was run over the tree with this file in place.

## Gaps and notes

- The Wolfram Community post at https://community.wolfram.com/t/25007 is listed twice under two spellings of its title: Geodesic congruence in casual graphs on DiscreteGeometry/GeodesicsAndDistance and Geodesic congruence in causal graphs on DiscreteSpacetime/RelativityAndFoliations. The first is a typo of the second; the audit treats them as one entry present on both pages.
- Wolfram/QuantumFramework Kernel/Multiway.m (fetched from GitHub main on 2026-09-21) exports exactly QuantumCircuitMultiwayGraph, QuantumCircuitMultiwayCausalGraph, QuantumCircuitTokenEventGraph and QuantumCircuitPathGraph, and Kernel/ZX.m exports ZXExpression, ZXTensorNetwork and ZXTensorNetworkQuantumCircuit. All seven are already in the tree (on BranchialGraphs and StringDiagrams); this audit cross-lists the multiway ones onto MultiwaySystems and CausalGraphs. No further multiway export of the paclet was found.
- Entries that no page describes: 28 of the cross-listed rows come from tail bullets or per-source runs with no description anywhere in the tree (among them the InfraCausality light cone and light ray constructors, the Infrageometry complex and topology helpers, the THVMLink prover bindings and the TuringMachine paclet's multiway helpers). Their descriptions in this report are written from the inventory usage text and should be checked against the source before they go on a page.
- The inventory's description of AlgebraicSubstitutionTiling says it is unrelated to the project's constraint-tiling work; it was dropped from the SyntheticGeometry candidates for that reason.
- The Function Repository function Geodesic (geodesics of a parametrized surface) resolves in the kernel but is not a twin of the technical introduction's Geodesics graph function; it is noted here so that a name match is not mistaken for one.
- The rows propose placements only. The house rules for the new bullets (a description written for the new page's angle, the tag or the per-source heading, chips and links in separate tail bullets, no per-source subsection for a handful of entries) apply when they are written; several pages will gain enough entries from one source to open a per-source subsection there (the TuringMachine paclet on MultiwaySystems, InfraCausality on RelativityAndFoliations, Infrageometry on SyntheticGeometry).
